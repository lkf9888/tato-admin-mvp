# TATO Evidence

车况存证拍摄 App（独立 iOS App，bundle id `co.tatocar.evidence`）。

引导员工按固定清单绕车拍照，当场判清晰度，**并保证交出去的是相机产出的原始文件**。

## 为什么要有这个东西

Turo 理赔部门拒收过本车队的照片，理由是「无法验证拍摄时间」。他们的规则是：
照片元数据必须有**日期、时间、地理位置**，缺一项即判无效；截图和转存副本不采信；
交车和还车各有 24 小时的上报窗口。

现有的 TATO Staff App 走的是 `expo-image-manipulator`，缩到 1800px、质量 0.74
重新编码 —— 那是在主动销毁证据。这个 App 存在的首要理由就是不那样做。

## 七条不能破的规矩

1. 相机原始文件直接落盘，不经过 `UIImage` / `Bitmap` / canvas
2. 拍摄当时写入**真实** EXIF：时间 + 时区 + GPS + 机型
3. **写完元数据再算 SHA-256**，顺序反了整条链作废
4. 上传原字节，服务端重算哈希比对，对不上拒收
5. 归档只读，标注/水印一律生成副本
6. 导出走 ZIP(STORED) → 电脑解压 → 直接上传，不经手机相册
7. 绝不伪造任何值，绝不给历史照片事后补 EXIF

## ⚠️ ImageIO 实测踩到的三个坑

这三条是在这台机器上跑出来的，不是推测。改 `ExifStamper` 之前先读。

### 坑一：`CGImageDestinationAddImageFromSource` 会重新编码

看起来是"复制图像 + 换元数据"的正解，实测**熵编码数据从 8614 字节变成 7664 字节**
—— 元数据完好，像素被悄悄重写了。这是最危险的一种失败：文件看着没问题。

✅ 正解是 `CGImageDestinationCopyImageSource` + `kCGImageDestinationMetadata`
+ `kCGImageDestinationMergeMetadata`。实测扫描数据逐字节一致。

> 所以 `ExifStampResult.imageDataUnchanged` 必须由调用方当硬失败处理。
> **光看"元数据还在不在"会被骗，哈希对得上才是铁证。**

### 坑二：GPS 时间戳必须写 ISO 8601，不能写 EXIF 原生格式

| 写法 | GPS IFD 里读出来 |
|---|---|
| `GPSDateStamp = "2026:09:10"`（EXIF 原生） | ❌ `1900:01:00` |
| 只写 `GPSDateStamp`，不写 TimeStamp | ❌ 日期对，时间被瞎编成 20:00:00 |
| ✅ `GPSTimeStamp = "2026-09-10T00:26:40Z"` | ✅ 日期和时间都正确 |

ImageIO 会自己把这一个 ISO 串拆成 `GPSDateStamp` + `GPSTimeStamp`。
**一个错的值比没有值严重得多** —— 证据文件里写错话是会被对方抓住的。

### 坑三：`GPSProcessingMethod` 这条路根本写不进去

四种写法都试了，tag `0x001B` 从来没进过 GPS IFD。所以**不写**，
把定位来源记在我们自己的 manifest 里。缺一个标签不说谎。

### 坑四：iOS 17+ 默认会把「延迟处理的占位图」当成照片给你

`AVCapturePhotoOutput` 在现代 iPhone 上会启用 **deferred photo delivery**，
`didFinishProcessingPhoto` 拿到的可能是 `AVCaptureDeferredPhotoProxy` ——
一个占位对象，真正的处理**在相册里稍后完成**。它能 flatten 出一坨看起来像照片的
东西，但那不是拍摄结果。

✅ `output.isAutoDeferredPhotoDeliveryEnabled = false`，在 `EvidenceCamera` 里写死了。

同一个地方还钉了两件事：
- **要 JPEG 不要 HEIC** —— 不是画质考虑，是因为文件要传给保险公司的网页上传器，
  事后把 HEIC 转 JPEG 就等于重编码。直接让相机产出 JPEG，零成本。
- **零快门延迟保持开启** —— 它从环形缓冲取帧，画面可能比按键早零点几秒。
  这没问题（EXIF 记的是帧的真实时间），而且能少掉一大截运动模糊。

### 还有一条方法论

**别用 ImageIO 验证 ImageIO 写的东西。** 它会拿 XMP 包重建出一个
`kCGImagePropertyGPSDictionary`，于是一个根本没有 GPS IFD 的文件看着完美 ——
而收件方的解析器不跑 ImageIO。测试里的 `RawExif` 是独立写的 TIFF/IFD 解析器，
断言一律对着它。

独立验证跑过：`sips` 读出 creation/make/model，Spotlight（`mdls`，完全独立的
导入器）读出 `kMDItemLatitude 49.19213833` / `kMDItemLongitude -123.1289166667`
/ `kMDItemAltitude 5` / `kMDItemContentCreationDate 2026-09-10 00:26:40 +0000`。

⚠️ 验证时别把文件放在 `/tmp` 或点号开头的目录 —— Spotlight 不索引那些地方，
你会得到一串 null，然后误判成元数据丢了（这个弯我已经绕过一次）。

## 两个写入器，两套 GPS 日期格式 —— 这不是笔误

| | 写入器 | GPS 日期格式 |
|---|---|---|
| `CaptureMetadata`（主路径） | AVFoundation，直接写 EXIF | EXIF 原生 `yyyy:MM:dd` + `HH:mm:ss` |
| `ExifStamper`（回退） | ImageIO，走它的 XMP 映射 | ISO 8601 —— 原生格式在这条路上会被写错 |

**别为了"一致"把其中一个改成另一个。** 两个写入器有两个不同的毛病，
哪个对是**在真机上运行时判定的**，不是在这里决定的：`MetadataFinisher` 把成品
读回来检查，主路径漏了什么就回退，用了哪条路记在每张照片的 manifest 里。

## 汇总页：闸门在这里才生效

每一道检查都产出一个事实，而**没人读的事实改变不了任何事**。
没有一个说「你还不能走」的地方，员工就是拍完 24 张、其中 3 张没位置，然后走人 ——
问题几个月后由保险公司告诉你，那时候车已经又租出去九次了。

所以汇总页不是回执，是**这趟绕车过关还是被打回**的地方。

| | 行为 |
|---|---|
| 还差几张没拍 | **拦住**，拍完才能交 |
| 缺位置 / 不在机位 / 手动放行 | **警告**，能交但必须先看见 |

警告不做成拦截是故意的：地下车库真的没信号，车真的会被堵在墙边。
一个拒绝让你收工的手机，最后会被换成系统相机。

## 判定策略：清晰度卡单张，元数据卡整单

- **清晰度不合格** → 这张不算数，重拍。拍满 3 次后允许员工「仍然使用」，
  但理由会记进 `acceptedDespite`，后台看得到是谁放的行。
- **缺位置信息** → 照片**照样存下来**（地下车库确实没信号，把人卡死在车边没有意义），
  但整个批次不能算完成 —— 汇总页会列出来要求到室外补拍。
  这样问题在停车场就暴露，而不是几个月后由保险公司告诉你。

`EvidenceCore` **刻意不 import ARKit 和 AVFoundation**，这样证据链规矩能在笔记本上
一秒钟测完，而不是只能在停车场里拿手机测。

## 拍摄清单：24 格

外观 16（4 个 45° 角 + 4 个正面 + 4 个轮 + 前后保险杠下沿 + 车顶 + 前挡风）
内饰 8（仪表台、里程表、油量、前排、后排、中控、顶棚、后备厢）

满足 Turo 的外观 ≥15 / 内饰 ≥8。`ShotPlanTests` 把这两个下限钉死了。

**没有底盘格位**，这是决定不是遗漏：Turo 不 cover 底盘理赔，而且手机也拍不了
—— 那是个遮挡、无光的空间，LiDAR 没有可测的返回面，ARKit 直接丢追踪。
替代的是前后保险杠下沿和四个轮胎下方，蹲下来拍。

## 绕车覆盖：一套 tracker，不是两套

最容易想歪的设计是「LiDAR 引擎 + 非 LiDAR 引擎」。那是错的 ——
**位姿追踪是 ARKit 的活，两种机器一样好。** 深度传感器唯一改变的是
「车的包围盒怎么建立」：自动量出来，还是手动标出来。

所以只有标定这一步分叉，下游全部是 `EvidenceCore` 里那套共用的、有测试的几何。

> 🔑 **LiDAR 买到的是免标定，不是精度。** 这句话值得记住 ——
> 它同时决定了产品能不能卖：车队现在全是 Pro 机，但 App Store 上的 Turo host
> 大多不是，一个必须 LiDAR 才能用的 App 卖不动。而且 Pro 机在强阳光下红外被淹没，
> 重建照样会悄悄停掉，那时候走的也是同一条降级路。

### ⚠️ PCA 只能找到车的轴线，找不到哪头是车头

主成分分析给的是一条**直线**，直线没有方向，而车的粗糙网格太对称，
分不出引擎盖和后备厢。所以 `fit(points:groundY:observedFrom:)` 用
**拍照人当时站的位置**来定方向：拍摄清单第一张就是「左前 45°」，
所以标定时离人近的那头就是车头。

**这就是清单第一张必须是车头方位的真正原因** —— 把清单顺序一改，
这里会不声不响地开始把人往车的反方向指。

### ⚠️ 两个参照系，说错一个人就走反

`CoverageGuidance.turnDegrees` 是**绕着车**量的（方位角顺时针增加）。
但站在车头前面面对车时，「绕车顺时针」是往你的**左手边**走。

没人应该在举着手机的时候现算这个。`Bearing.relative(to:from:facing:)`
把它转成拍照人自己的参照系，界面上的箭头用的是这个。
有一条测试专门钉死这个矛盾：同一个目标机位，绕车方向是正的，人的方向是负的。

### ⚠️ 只看方位角认不出机位

`front_three_quarter_right` 在 45°，`wheel_front_right` 在 60° ——
差 15°，落在任何可用的角度容差里面。真正分开它们的是**高度和距离**：
一个站着后退三米半拍，一个蹲着贴近拍。三个轴一起打分，
否则半个绕车流程会在错误的位置上把自己勾掉。

容差是**故意放宽**的（角度 ±22.5°、距离 ±1.5m、高度 ±0.6m），
而且 45° 的机位间隔配 ±22.5° 的容差**刚好铺满整圈没有死区** ——
留死区就是让员工站在停车场里等手机想明白。这个是要抓「同一个角落拍了四张
就说自己绕了一圈」，不是要把人赶到某个点上站好。

### 位置对不对：记录，不拦截

拍的时候如果人不在指定机位，**不挡快门**（追踪抖一下就拒绝拍照，
会把人晾在车边），而是把 `stationVerified` 记进每张照片。
汇总页再说「这 3 张不是在指定位置拍的」。追踪不可用时记 `nil` ——
那既不能证明合格也不能证明不合格，不该算在谁头上。

### ⚠️ 读网格顶点要一次读三个 float

ARKit 的顶点按 **12 字节步长**打包，而 `SIMD3<Float>` 的步长是 16 字节、
还要求 16 字节对齐。把 buffer 绑成 `SIMD3<Float>` 去读**看起来是对的、能编译**，
然后一边读错位的垃圾数据一边冲出几何体的尾部。

## 交单路径：为什么最后还是走相册

Kevin 的车队用 **Turo 手机 App** 报案，而那个 App 的选图器只读系统相册。
所以照片**必须**进相册 —— 这一点绕不开。

> **相册那份是投递副本，不是档案。** 档案仍然在 App 自己的容器里：
> 只读、有哈希、有 manifest。相册那份丢了、被删了、被人编辑了，都不影响档案。

写进相册用 `PHAssetCreationRequest.addResource(with: .photo, data:)` ——
它按给的字节原样存。**绝不能走 `UIImage`**，那一步就是重编码。

### ✅ 实测（模拟器）：相册这条路是无损的

在 App 容器里种一份真归档（含一张已知 EXIF/哈希的照片），
把同一张加进模拟器相册，再用「路径自检」从相册选出来：

| 项 | 结果 |
|---|---|
| 拍摄时间 | ✅ `2026:09:09 17:26:40` |
| 时区 | ✅ `-07:00` |
| 位置 | ✅ `49.192139, -123.128917` |
| 和归档原件 | ✅ **字节完全一致** |

所以系统选择器（`PhotosPicker` / `PHPickerViewController`，和第三方 App 用的是同一个）
**返回的是原文件，GPS 没被剥掉**。这对 Turo App 那条路是好消息。

### ⚠️ 但有一个开关会毁掉它

系统选图器底部有一个 **「Location Is Included」** 开关，用户可以关。
关掉之后位置就没了，**而且界面上不会有任何提示**。

所以「路径自检」不是做完就扔的工具 —— 换手机、升级系统、或者有人手贱关了开关，
都要重新验一次。这也是为什么自检做成 App 里的一页，而不是文档里的一句结论：
我在文档里断言「iPhone 这条路安全」，迟早会过时而没人发现。

⚠️ **以上全部是模拟器结果，真机必须再验一遍。**
而且真机上还有一件事这里测不到：Turo 自己的 App 拿到文件之后怎么处理。
那一段我们看不见，只能靠「传上去之后看 Turo 认不认」来倒推。

## 后端：服务端不信客户端说的任何话

照片除了进相册交给 Turo，还会传一份到车队自己的后台。相册那份是**投递副本**，
后台这份是**留底** —— 员工手机丢了、删了、换了，这份还在。

代码在主仓库这边：

```
lib/inspection-evidence.ts   EXIF 解析 + 校验（零依赖，手写 TIFF/IFD）
lib/inspection.ts            开单、存图、判完成
app/api/inspection/…         三个路由
scripts/check-inspection-evidence.ts   自检，npx tsx 跑
prisma/migrations/202609190002_inspection_sessions/
```

### 拒收什么，记录什么

| | 处理 |
|---|---|
| 哈希和字节对不上 | **400 拒收** —— 传输坏了或者发的人在撒谎，两种都让文件失去证据价值 |
| 不是 JPEG | **415 拒收** |
| 没有拍摄时间 | **422 拒收** —— 这只可能是 bug，存下来也永远用不了 |
| 同一格同一次、字节不同 | **409 拒收** —— 静默覆盖会毁掉其中一份 |
| **缺位置** | **照收，记进 `evidenceGaps`** |

⚠️ 最后一条是故意的，别改成拒收。地下车库真的没信号，而那张照片仍然是那天那个保险杠
唯一的影像。拒收它等于**用我们拿得到的证据，去换我们拿不到的证据**。
缺口记在库里，整单不能标完成，问题在停车场就浮出来。

### 只有服务端能做的一件事：对表

手机的时间是用户可以随便改的，所以 EXIF 时间的可信度上限就是写它的那台设备。
上传时客户端把自己的当前时钟一起发过来，服务端拿自己的时间减一下 ——
差超过两分钟就标 `clockSuspect`。这是唯一一个客户端做不到的交叉验证。

### ⚠️ 服务端**验不了**的事

服务端能验**传输完整性**（字节和声称的哈希一致）和**元数据充分性**（理赔要的字段齐不齐），
但验不了**来源** —— 它没见过相机，没法判断这堆字节是不是原件。

实测过：把 `known.jpg` 用 `sips` 重新编码一遍，EXIF 全部幸存（时间、时区、GPS 都在），
只有哈希变了。服务端收到这种文件会正常接受。

**所以原件这件事只能在客户端守**：`MetadataFinisher` 的 `imageDataUnchanged` 检查、
归档时算哈希、以及「路径自检」那一页。服务端是第二道，不是第一道。

### 实测（本地 dev server 全链路跑过）

| 场景 | 结果 |
|---|---|
| 开单，车牌 `TV951F` | ✅ 自动匹配到车辆行 |
| 同一个 clientSessionId 再开一次 | ✅ `resumed: true`，不会开出第二单 |
| 传 Swift 写出来的真照片 | ✅ 服务端自己算的哈希和 Swift 一致，`gaps: []` |
| 同一张再传一次 | ✅ `duplicate: true`，不报错 |
| 哈希填错 | ✅ 400 `DIGEST_MISMATCH` |
| 传个文本文件 | ✅ 415 `NOT_A_JPEG` |
| 同格同次换一张图 | ✅ 409 `SLOT_CONFLICT` |
| 还差一张就交单 | ✅ 409 + `missingSlotIds` |
| 手机时钟快 2 小时 | ✅ `clockSuspect: true`，但**不拒收** |
| 交单 | ✅ 200 + 后台自己复核出的四类警告 |
| 交完再加照片 | ✅ 409 `SESSION_ALREADY_COMPLETE` |
| 不带 token | ✅ 401 |

落盘文件逐个重算哈希，和库里记的全部一致。

### ⭐ 跨语言交叉验证

Swift 写出来的 JPEG，用 TypeScript 那个**独立写的**解析器读：

```
sha256    88828cfce8867871eb0f3e4031a85e24bc31b34da0ea47be4647eec54cadd53b   ← 一致
location  49.192138888888884, -123.12891666666665                            ← 到最后一位一致
capture   2026:09:09 17:26:40 -07:00                                         ← 一致
```

两个独立实现在同一个文件上对得上，说明写进去的是**标准 EXIF**，
不是只有 Apple 自己的框架认识的东西。这正是 Turo 那边的解析器要读的。

### 两个列表，顺序是有讲究的

**「还没拍的」排在前面。** 一单行程的 24 小时窗口正在关闭而照片没拍，
那是钱在往外流，而且**不放到屏幕上就完全看不见**。归档反而排后面 ——
那个是已经有争议了才会去翻的。

窗口过期**是一个状态，不是一个过滤条件**。已经来不及的那几单必须留在页面上：
它们是「这套流程没在运转」的唯一证据，过期就藏起来等于把问题一起藏了。

### 并排对比才是重点

一张刮痕的照片只能证明刮痕存在，**只有交车时同一个角度的照片才能证明是租客弄的**。
所以详情页按机位排版，不按批次:左边交车、右边还车，眼睛自己去比。

### ⚠️ 配对必须有时间上限（`MAX_PAIR_GAP_DAYS = 30`）

不加限制的话，一次还车会和它之前**任何**一次交车配上 —— 哪怕那是六个月、
九次出租之前的。页面会把两张照片并排放在「交车 / 还车」两个标题下面，
看的人一扫而过就会把三次行程之前的损伤算到这位租客头上。

差得太远就说明我们说不清是谁那一趟，**诚实的做法是干脆不配对**。

这个是在跑页面时发现的 —— 我造的测试数据顺序反了，配不上，
顺着查下去才意识到没上限的版本更危险。

### ⚠️ 图片用原生 `<img>`，不用 `next/image`

这个归档的全部意义就是字节是相机自己产出的。
上一个优化器会重新编码，然后页面上给看的人看的就**不是证据本身**了。
「保存图片」也一样：存下来的必须是原件，不是派生图。

## ⚠️ 清晰度阈值还没标定

`ImageQualityThresholds.provisional` 里的数字是**占位的**。Laplacian 方差不是绝对量，
随光照、车漆颜色、拍摄距离大幅漂移，抄论文或抄别的 App 的数在这里没有意义。

标定步骤：

1. 让员工用平时那套操作，在真实场地拍 50–100 张，糊的清楚的都要
2. 人工标注每张「能用 / 不能用」
3. 跑 `ImageQualityGate` 收集分数，找分界
4. **阈值往严了压**：误判成糊只损失一次重拍，漏判一张糊的要赔一次车

标定之前不要让员工依赖这个闸门。

⚠️ 汇总页只验证了编译和逻辑（`SessionReadiness` 有测试），**界面本身还没跑起来看过** ——
要走到那一页得先拍完一批，而模拟器没有摄像头。

接下来：真机验证 —— 这是现在唯一挡在路上的事。
步骤清单在 **[DEVICE-CHECKLIST.md](DEVICE-CHECKLIST.md)**，
另有一份能在手机上打勾的同版本（打的勾跨设备保存）。

⚠️ **相机这条路一行都还没在真机上验过。** 模拟器没有摄像头，
所以到目前为止验证的是「代码能编译、失败路径不崩」，不是「拍出来的照片合格」。
第一件要做的事是拿真机拍一张，把文件导出来跑 `ExifReader`，
确认 `metadataPath` 报的是 `writtenAtCapture` 而不是每张都在回退。

⚠️ **AR 同样一行没在真机上验过。** 几何和拟合算法是用合成点云测的 ——
那能证明数学对，不能证明 ARKit 在真实停车场给的数据长什么样。
要拿真车试，而且必须试黑车、白车、强阳光三种：黑漆和玻璃对红外是镜面，
网格上会有洞；强阳光下红外被淹没，重建会退化。
室内对着小物件的表现完全不能外推。

⚠️ 还有一件事只能在真车上定：`VehicleFrameFitter.bodyHeightRange`（0.25–2.2m）
和 `VehicleFrame.isPlausible`（长 3.0–6.5m、宽 1.4–2.4m）这两组数是按常见轿车/SUV
拍的，遇到皮卡或者带车顶架的车可能会被判成「不像一台车」而退回手动标定。
真车试过再收紧或放宽。
